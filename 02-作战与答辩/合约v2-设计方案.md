## 1. 目标口径

v2 只解决一件事：**把"定价"与"投保时刻"从写死的常数，变成按（区域 × 时长 × 险种）可表达的参数，并堵住两个会被套利的口子（知情入场 / 不限购）。**

判定层不动。理由：它是我们最结实的一块，也是"可审计"的落点；改它只有风险没有收益。

## 2. 三处必须先拍板的设计抉择（它们互相影响）

### 抉择①：A2「阈值随窗口缩放」还是 A7「按强度分档」？—— ✅ 落地定为**「以 A2 为基准线的 A7（国标三级）」**（2026-10-07 更正）

> ⚠️ **本节原先写的是"二选一，不要都做"。落地（`57f612e`）时发现那个框法本身是错的** —— 见下。

两者不是并列的两个机制，而是**同一个机制的两半**：**A7 的档线必须有基准线**。国标（GB/T 28592-2012）的三条强度线是**24 小时口径**（暴雨 50 / 大暴雨 100 / 特大暴雨 250 mm 每 24h）。把它用在 24/48/72h 的窗口上只有两种写法，而两者**数学上等价**：

| 写法 | 基准线 | 72h 档上的阈值 |
|---|---|---|
| 按**平均强度**判（原文 A7） | 强度线 50/100/250 mm 每 24h | 4.17 / 8.33 / 20.8 mm/h |
| 按**累计量**判（✅ 落地实现） | `thresholdOf(h) = 50 × h / 24` | 150 / 300 / 750 mm |

所以实现 = **`thresholdOf(h)` 提供基准（原文的 A2）+ `tierOf` 在基准上取 ×1 / ×2 / ×5 三档（原文的 A7）**。原文担心的"72h 下既要 150mm 又要 4.17mm/h"**是同一条件的两种单位表达，不是叠加**。

| | 原文 A7（强度四档 25/50/75/100%） | **落地实现（国标三级 50/75/100%）** |
|---|---|---|
| 档线 | 4.17 / 8.33 / 16.7 / 33.3 mm/h | `base × 1 / 2 / 5`，`base = 50 × h / 24` |
| 赔付 | 0.0025 / 0.005 / 0.0075 / 0.01 | 0.005 / 0.0075 / 0.01 |
| 出处 | 我按四色预警信号推的 | **GB/T 28592-2012 的暴雨 / 大暴雨 / 特大暴雨** ← 更可举证 |

**代价（B 用 11 年逐小时数据实跑，`cd 10-金融与定价 && node audit_numbers.js --self-check` → 17 项 PASS）**：**24h 档三档里 0/1 档可达**（1 档 0.04%–0.13%）；**48h/72h 的 1 档几乎不可达**（72h 1 档只有武汉 50 次）；**2 档在 11 年里 0 次**（72h 要 750mm，实测最大武汉 392.4mm）。所以演示落 **0 档 → 赔 50%**。详见 `02-作战与答辩/定价-v2分档影响-B给A的量化.md` §七。

> ⚠️ **无论选哪个，都会改变演示动线**（见 §4）：现在"广州 50mm 正好压线、成都 120mm 满格"这个效果，是建立在 `阈值恒为 50` 之上的。

### 抉择②：A4 冷静期会打断"现场投保、现场理赔"—— 三选一

`t+3` 冷静期一加，**刚买的保单在 3 天内不可理赔**，我们最有力的那条动线（买 → 喂价 → 判定 → 点申请赔付）当场断掉。

| 方案 | 怎么做 | 代价 |
|---|---|---|
| ②-1 **`coolingPeriod` 可配置**（operator 可设，带事件）← **最务实** | 演示/彩排设 **0**，生产设 **3 days** | 削弱说法："operator 能关掉冷却期" —— 必须主动交代，且有链上事件留痕 |
| ②-2 **日历窗口 + 售前截止** | 保单保"某个未来窗口"，且必须窗口开始前买；演示时把窗口设成"买的下一刻" | 窗口逻辑更复杂；状态机多一段 |
| ②-3 **演示用一张已过冷静期的历史保单** | 链上先放一张上周买的保单，现场演示它的理赔 | 现场"买一张新的"仍不能马上赔，动线分裂成两条 |

**我建议 ②-1**（诚实交代 + 事件留痕），并把 ②-2 写在 roadmap 上。

### 抉择③：A6 的自动准备金 —— 循环不可接受，需要"敞口账本"

```solidity
// ❌ 不要这么写：nextPolicyId 一大，gas 就爆
for (uint256 i = 0; i < nextPolicyId; i++) { ... }
```

正解：维护一个**在保敞口累加器**，谁变更谁记账：
- `buyPolicy` → `openExposure += payoutOf(档位)`
- `claim` 赔付成功 → 由 operator 调 `settle(policyId)` 或 `claim` 内直接 `-=`
- **过期未赔**的保单也有敞口 → 需要一个 `settleExpired(uint256[] ids)`（operator 调用，事件留痕）

**代价**：多一个运维动作（每天结算到期敞口），否则 `openExposure` 会虚高、准备金要求偏高。这一条必须写进方案，否则 v2 会带来"准备金只涨不落"的新毛病。

## 3. 逐条接口设计

### A1 保费（区域 × 时长）

```solidity
uint256 public constant MIN_PREMIUM = 0.0002 ether;   // 保费地板（依据：一笔投保链上手续费≈0.00046 ETH）
uint256[3] public HOUR_TIERS = [24, 48, 72];          // 只卖三档（合约层白名单）

mapping(uint8 => mapping(uint256 => uint256)) public premiumGrid;  // regionId => hours => premium

function premiumOf(uint8 regionId, uint256 hours) public view returns (uint256) {
    uint256 p = premiumGrid[regionId][hours];
    if (p == 0) p = aiPremium[regionId];       // 回退：区域基础价
    if (p == 0) p = PREMIUM;                    // 再回退：默认价
    require(p >= MIN_PREMIUM, "premium below floor");
    return p;
}

function hoursAllowed(uint256 h) public pure returns (bool) {
    return h == 24 || h == 48 || h == 72;
}
```

- `buyPolicy(uint8 regionId, uint256 hours)`：`require(hoursAllowed(hours))`、`require(msg.value == premiumOf(regionId, hours))`
- 新增 `setPremiumGrid(uint8 regionId, uint256 hours, uint256 premium, bytes32 reasonHash) external onlyOperator` + 事件 `PremiumSet(regionId, hours, premium, reasonHash)`
- **连带**：`04-脚本/set-premium.js` 从 5 个值变 15 个（已有 `--hours=N` 参数）；定价设计页直接可用；演示页 `hoursInput` 三档已就位，只需把 `premiumOf(region)` 改成 `premiumOf(region, hours)`

### A7 赔付分档（✅ 已落地为「以窗口缩放线为基准的国标三级」）

```solidity
// 档线全部链上可算 —— 不需要 AI 参与，红线那句话继续成立
uint256 public constant THRESHOLD_PER_24H = 50;            // 国标暴雨线
function thresholdOf(uint256 hours) public pure returns (uint256) {   // 基准线（原文 A2）
    return THRESHOLD_PER_24H * hours / 24;
}
function tierOf(uint256 duringMm, uint256 hours) public pure returns (uint8) {
    uint256 base = thresholdOf(hours);
    if (duringMm >= base * 5) return 2;   // 国标特大暴雨 → 100%
    if (duringMm >= base * 2) return 1;   // 国标大暴雨   → 75%
    if (duringMm >= base)     return 0;   // 国标暴雨     → 50%
    return 255;                           // 不达标
}
function tierBps(uint8 tier) public pure returns (uint256) {
    if (tier == 2) return 10000;
    if (tier == 1) return 7500;
    return 5000;                          // 0 档（caller 侧仍有 TIER_NONE 保护）
}
```

- `claim` 里 `during >= THRESHOLD` 换成 `tier != 255`，打款额 = `PAYOUT_MAX * tierBps(tier) / 10000`
- ⚠️ **1/2 档在 11 年数据里几乎不可达**（48/72h 的 1 档近 0，2 档恒 0；**24h 档的 1 档可达 0.04%–0.13%**）→ 这是"国标线本来就高"的正常后果，**答辩要主动说**，不要等着被问
- **B 已按分档重算**：期望赔付 = `Σ P(tier_k) × payout_k`；15 格公平保费落在 **9.08e-6 ~ 1.24e-4 ETH，全部低于地板 `MIN_PREMIUM` 0.0002** → 结论是"v2 下真正贵的不是风险，是每笔交易的固定成本（链上约 2.5e-4/笔）"
- 落地时另修一处合约缺陷（`withdrawPool` 在 `reserveOf() > balance` 时 uint256 下溢成 `Panic(0x11)`）→ 改成先比大小再相减，见 §A6

### A4b 喂价新鲜度（B 在 §6.5 提的"喂价时点基差"—— **A 确认成立，并给出修法**）

问题：`during = rainfall[regionId] − rainfallAtBuy`（`:250`），而 `rainfallAtBuy` 取的是**投保时最后一次喂价**的累计值。若那次喂价早于投保时刻，`during` 会把**投保前**的降雨也算进来。

两个后果：
- 精算侧：`p` **被高估**（方向保守，但也意味着我们算出来的应需保费偏高）；
- 套利侧：这就是 `待解决问题清单-10-07.md` **P1-19** 的那个洞 —— 雨已落地但未喂价时买票，把"投保前的那场雨"变成自己的增量（`0.0008 × 5 张 → 拿走 0.0512 池子`）。

```solidity
mapping(uint8 => uint64) public lastFeedAt;          // 每区域最后喂价时间
uint64 public constant MAX_FEED_AGE = 24 hours;      // 喂价新鲜度上限

// buyPolicy 内：
require(block.timestamp - lastFeedAt[regionId] <= MAX_FEED_AGE,
        "stale feed: feed before buying");
// updateRainfall 内：lastFeedAt[regionId] = uint64(block.timestamp);
```

这条 require 把"投保前必须先喂价"从**操作纪律**变成**合约层硬约束**（我们自己的流程本来就是先喂价后投保，但那只是纪律，不是约束）。
**代价**：operator 必须至少每 24 小时喂一轮五城；演示动线要改成"先喂一次 → 再买"。
**与 A4 的关系**：**A4 堵"窗口"（买得太晚），A4b 堵"基线陈旧"（久不喂价）—— 两条一起才算闭环。**

### A6 准备金自动规则（配合抉择③）

```solidity
uint256 public openExposure;                      // 在保敞口（累加器）
uint256 public constant RESERVE_BPS = 10000;      // 演示用"资本充足口径"= 100% 敞口
function reserveOf() public view returns (uint256) { return openExposure * RESERVE_BPS / 10000; }
// withdrawPool：require(amount <= balance - reserveOf(), "reserve breach")
// setReserve 保留（作为下限的额外加成），但不得低于 reserveOf()
```

> **落地时改了（2026-10-07，本地 e2e 逼出来的）**：上面那行 `balance - reserveOf()` 有一个
> 真缺陷 —— `reserveOf()` 是"应该留多少"，它可以**大于**当前余额（例如刚买完保单、池子还没注够），
> 此时 `balance - reserveOf()` 是 **uint256 下溢**，会抛 `Panic(0x11)`，第三方拿到的是
> `Panic due to OVERFLOW(17)` 而不是人话。已改成先比大小再相减：
> ```solidity
> uint256 bal = address(this).balance;  uint256 res = reserveOf();
> uint256 free = bal > res ? bal - res : 0;
> require(amount <= free, "would break reserve");
> ```
> 注意这不是"测试写错了"，是测试**先于部署**发现了合约缺陷 —— 正是 e2e_v2 存在的意义。
